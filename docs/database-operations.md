# AEGIS — Database Operations, Synchronization & Storage Guide

**Version:** 1.0.0 (Release Candidate)  
**Author:** Apri (Senior Software Engineer, Database Architect)  
**Classification:** Operational Engineering Manual  

---

## 1. Overview & Storage Topology

The AEGIS database subsystem manages operational security data across two physical storage engines:
1. **Supabase Cloud (PostgreSQL 15.8):** Multi-tenant, scalable cloud database acting as the primary SSoT in Stage 2.
2. **Local SQLite (`aegis_incidents.db`):** High-speed local embedded database operating in Write-Ahead Logging (`WAL`) mode, acting as primary in Hybrid mode and cold durability replica in Cloud SSoT mode.

---

## 2. Table Catalog & Schema Mapping

The database comprises 13 operational tables organized across two primary domains:

### Domain A: Telemetry & Host State (Cloud Primary)
1. **`hosts`:** Registered Linux nodes, hostnames, agent versions, heartbeats, and status (`online`, `offline`, `archived`).
2. **`system_status`:** High-level health flags for collector, detection rules, and AI providers.
3. **`telemetry_events`:** Ingested Linux system logs, authentication attempts, PAM sessions, process executions, and network sockets.
4. **`alerts`:** Deterministic alerts generated by the Rules Engine.
5. **`alert_evidence`:** Composite junction table `(alert_id, event_id)` linking alerts to concrete telemetry evidence.

### Domain B: Incidents & Security Posture (SSoT & Local Mirror)
6. **`security_check_runs`:** Metadata for automated Linux CIS hardening evaluations.
7. **`security_findings`:** Individual compliance findings linked to check runs via `run_id`.
8. **`incidents`:** Correlated security incidents with severity, risk score, status, and pivot entities.
9. **`incident_alerts`:** Junction table linking discrete alerts to parent incidents.
10. **`incident_risk_factors`:** Granular risk score contributors (e.g. brute force, privilege escalation, off-hours).
11. **`incident_timeline`:** Chronological audit trail of alert additions, status changes, and investigative notes.
12. **`ai_analyses`:** Grounded AI investigation results, hypotheses, facts, attack scenarios, and containment steps.
13. **`incident_status_history`:** Immutable lifecycle audit history for incident status changes.

## 3. Operational Mode Definitions

### A. Mode 1: `HYBRID` (Current Production Baseline)
- **Environment Key:** `AEGIS_DATABASE_MODE=hybrid` (or unset default)
- **Authoritative Database:** Local SQLite (`data/aegis_incidents.db`)
- **Operations:**
  - Incidents, risk factors, timelines, AI analyses, and security checks are written to and read from SQLite.
  - Telemetry events and host heartbeats are posted directly to Supabase Cloud REST endpoints.
  - No background catch-up or reverse mirroring is required.

### B. Mode 2: `CLOUD_SSoT` (Target Stage 2 Topology)
- **Environment Key:** `AEGIS_DATABASE_MODE=cloud_ssot`
- **Authoritative Database:** Supabase Cloud PostgreSQL
- **Operations:**
  - All read queries and write mutations execute against Supabase Cloud via `service_role`.
  - Mutating operations asynchronously mirror updates into local SQLite (`aegis_incidents.db`).
  - Failed mirror writes are logged durably in SQLite table `mirror_sync_log`.
  - Startup catch-up reconciles any unmirrored Cloud records before opening traffic.

## 4. Mirroring & Synchronization Mechanisms

### A. Asynchronous Local Mirroring
When running in `cloud_ssot` mode, every write to Cloud is mirrored into SQLite:
1. Transaction commits successfully in Cloud PostgreSQL.
2. An asynchronous background task invokes `SqliteIncidentStore.upsert_*`.
3. If SQLite write succeeds, transaction completes with zero overhead.
4. If SQLite write fails (e.g., temporary disk lock):
   - The failure is logged in SQLite `mirror_sync_log` with status `pending`, timestamp, table name, and primary key.
   - The background worker `_periodic_mirror_worker` replays failed mirrors every 60 seconds.

### B. Startup Catch-Up Engine (`catch_up_unmirrored_from_cloud`)
When the backend starts up in `cloud_ssot` mode:
1. It validates Cloud connectivity.
2. It replays any pending entries from `mirror_sync_log`.
3. It queries Cloud across all 8 operational tables in topological DAG order:
   - `security_check_runs` -> `security_findings` -> `incidents` -> child tables.
4. **Pagination:** It uses unbounded batch pagination (1,000 records per page) to ensure full reconciliation without truncation.
5. **Watermark:** It stores progress in `catch_up_watermark` table to allow idempotent resumption if interrupted.
6. **Content Comparison:** It updates SQLite if substantive business attributes (`status`, `severity`, `risk_score`) have changed in Cloud.
7. Only after catch-up successfully finishes does the state machine transition to `CLOUD_SSoT` with `is_catch_up_completed=True`.

## 5. Reverse Synchronization Engine (`scripts/sync_cloud_to_sqlite.py`)

Used during planned rollbacks, maintenance, or disaster recovery reconciliation:

### Command Usage
```bash
# 1. Read-only dry run (Safe, no disk writes)
python3 scripts/sync_cloud_to_sqlite.py --db-path data/aegis_incidents.db

# 2. Execute live synchronization with automatic pre-sync backup
python3 scripts/sync_cloud_to_sqlite.py --db-path data/aegis_incidents.db --sync --confirm

# 3. Force Cloud wins (override newer local timestamps)
python3 scripts/sync_cloud_to_sqlite.py --db-path data/aegis_incidents.db --sync --confirm --force-cloud-wins
```

### Safety Rules Enforced:
1. **Pre-Sync Snapshot:** Automatically creates timestamped snapshot `presync_backup_YYYYMMDD_HHMMSS.db` with matching `.sha256` hash.
2. **Topological Order:** Reconciles tables in parent-child foreign key order.
3. **Timestamp Conflict Detection:** If SQLite has a newer timestamp than Cloud, reverse-sync records a conflict entry in `conflict_report_YYYYMMDD_HHMMSS.json` and rolls back the transaction unless `--force-cloud-wins` is provided.
4. **Zero-Deletion Policy:** Local-only records are never deleted; only missing Cloud records are inserted or updated.
